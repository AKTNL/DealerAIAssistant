# P2 产品化增强任务总览

## Goal

把路线图中的 P2 产品化能力拆成边界明确、依赖可追踪、能够独立开发和验收的任务树。在任务拆分和顺序确认前，除已开始的 P2-1A 外不继续扩大实现范围。

## What I already know

* `docs/07-生产化升级路线图.md` 将 P2 分为完整用户权限、多租户和数据隔离、订阅推送与协作、运维和成本治理四个工作流。
* P2-1A 已有独立 PRD，并已完成“身份表结构与 Spring Security 基础”增量；登录会话、管理 API、业务授权收敛和文档迁移尚未完成。
* P1 已保留 `scope`、active import batch、报告 `scope_type/scope_id`、受控 Agent 和模块化单体边界，P2 应沿这些扩展点演进，不重写已验证链路。
* 组织范围必须先于完整 tenant 隔离；tenant 隔离必须先于 tenant 级知识、模型、导入、报告和订阅。

## Requirements

* P2 使用一个计划总览、四个工作流父任务和十五个可执行子任务管理。
* 每个可执行任务必须有独立 PRD，写明目标、依赖、交付、验收、失败边界和明确的不做项。
* 安全边界按“身份与功能权限 -> 组织范围 -> tenant 所有权与隔离 -> tenant 级资源”顺序推进。
* 订阅、推送、协作必须复用报告、权限、组织和 tenant 上下文，不建立旁路数据访问。
* 可观测性基线应尽早进入请求、模型、导入和报告链路；成本归集在 tenant 上下文完成后接入。
* 每个任务结束时都要同步自动化测试、OpenAPI/配置/运行文档以及发布回滚说明中与其相关的部分。

## Task Map

### P2-1 完整用户权限与组织范围

1. **P2-1A 身份、RBAC 与会话基础**：真实用户、opaque access/refresh session、固定权限目录、数据库角色、管理 API、安全审计、业务授权收敛和旧 shared-key 移除。
2. **P2-1B 组织树与数据范围**：组织层级、用户/角色范围授权、经销商映射、统一授权上下文，以及 Dashboard/数据/Agent/知识/报告的范围过滤。
3. **P2-1C 权限与组织管理界面**：用户、角色、组织、授权和会话管理 UI；前端权限入口与危险操作确认。

### P2-2 多租户和数据隔离

1. **P2-2A tenant 基础模型与迁移**：tenant 所有权模型、稳定 ID、现有数据回填和前向迁移。
2. **P2-2B tenant 隔离强制执行**：请求上下文、默认拒绝、查询/写入隔离、复合约束和跨租户攻击回归。
3. **P2-2C tenant 级平台资源**：模型配置、知识库、导入批次、报告历史和组织配置的 tenant 化。
4. **P2-2D tenant 发布与隔离验收**：迁移演练、双租户端到端矩阵、运维诊断、发布与回滚。

### P2-3 订阅、推送和协作

1. **P2-3A 报告订阅与调度定义**：范围、频率、时区、收件人、权限快照和订阅生命周期。
2. **P2-3B 可靠任务执行**：持久化作业、幂等生成、重试、并发控制、失败记录和补偿。
3. **P2-3C 通知投递通道**：统一投递端口、邮件/企业协作平台适配、凭据治理和投递回执。
4. **P2-3D 报告协作工作流**：评论、处理状态、负责人、操作历史和范围内协作通知。

### P2-4 运维和成本治理

1. **P2-4A 可观测性与全链路追踪**：结构化日志、trace/request/job 关联以及模型、导入、报告事件。
2. **P2-4B 模型使用与成本治理**：调用次数、耗时、token、费用、预算和用户/tenant/场景归集。
3. **P2-4C 健康检查、告警与性能**：readiness/liveness、依赖健康、慢查询、作业失败和告警策略。
4. **P2-4D 部署与运维加固**：生产配置校验、备份恢复、迁移检查、灰度/回滚和运行手册。

## Dependency Order

```text
P2-1A -> P2-1B -> P2-1C
                 \
                  -> P2-2A -> P2-2B -> P2-2C -> P2-2D

P2-1A -> P2-4A -> P2-4C
P2-2B + P2-4A -> P2-4B

P2-2B -> P2-3A -> P2-3B -> P2-3C
                 \-> P2-3D

P2-2D + P2-3C + P2-3D + P2-4B + P2-4C -> P2-4D
```

允许在依赖满足后并行开发，但同一数据库迁移、授权上下文或共享前端认证状态不得由多个任务同时修改。

## Delivery Waves

1. **身份闭环**：完成 P2-1A 的剩余增量。
2. **组织与观测基线**：P2-1B；P2-4A 可在 P2-1A 稳定后并行启动。
3. **管理面与 tenant 基础**：P2-1C、P2-2A。
4. **隔离闭环**：P2-2B、P2-2C、P2-2D。
5. **运营能力**：P2-3A 至 P2-3D，同时完成 P2-4B/P2-4C。
6. **生产收口**：P2-4D 与整套 P2 验收。

## Acceptance Criteria

* [ ] 四个 P2 工作流均有父任务，十五个执行任务均有独立任务目录和 PRD。
* [ ] 每个任务写明前置依赖、后续消费者、数据库/安全影响和质量门。
* [ ] 任务顺序不会在组织范围完成前宣称 tenant 隔离，也不会在 tenant 隔离前开放 tenant 级订阅或知识摄取。
* [ ] 当前 P2-1A 实现进度被保留，并能继续按原 PRD 的小增量执行。
* [ ] `task.py list` 能显示完整层级，且当前活动任务恢复为 P2-1A。

## Definition of Done

* 任务树和所有 PRD 通过结构检查。
* 依赖、范围、验收和不做项不存在明显冲突。
* 用户确认任务颗粒度和推荐实施顺序后，再继续编码。

## Open Questions

以下问题不阻塞任务拆分，在进入对应任务前逐项确认：

* P2-2 首个试点是单品牌多集团，还是集团下多品牌 tenant。
* P2-3 首个投递通道优先邮件、企业微信、钉钉还是飞书。
* P2-3D 首版是否只做状态/负责人，还是同时包含线程化评论。
* P2-4B 成本治理首版只观测，还是同时启用硬预算和熔断。

## Out of Scope

* 本任务只完成规划和任务建模，不实现新的业务代码。
* 不在任务拆分阶段提前选择具体消息队列、调度器或监控 SaaS。
* 不在 P2 内拆微服务；继续使用模块化单体，除非后续独立 ADR 明确改变。
* 不把 PDF/Word 导出、任意文档摄取、SSO 或 service account 自动并入现有任务；这些需要独立产品决策。
