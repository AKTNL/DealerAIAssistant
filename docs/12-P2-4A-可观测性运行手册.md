# P2-4A 可观测性运行手册

## 1. 适用范围

本手册覆盖 HTTP、SSE、Agent/模型调用、数据导入、报告生成、报告 job、报告投递和协作通知的本地诊断与 OTLP 对接。应用以 Micrometer Observation 为业务接口，以 OpenTelemetry bridge 生成标准 trace/span；不依赖特定监控厂商，也不在应用内保存或搜索 trace。

生产配置默认仅暴露 `health,info`。本地默认额外暴露 `metrics,prometheus`，便于开发诊断。

## 2. 关联契约

### 2.1 HTTP 与异步边界

* 入站 `X-Request-ID` 必须匹配 `[A-Za-z0-9][A-Za-z0-9._:-]{0,127}`；缺失、非法或超长值会被替换，不会截断后继续使用。
* 响应返回最终采用的 `X-Request-ID` 和当前标准 `X-Trace-ID`。
* W3C Trace Context 为出站格式；入站兼容 W3C、B3 single 和 B3 multi。
* SSE 在工作线程恢复当前 trace 与 request MDC。
* 延迟 job 创建新的执行 observation，通过持久化关联 ID 和 job/report/delivery/event ID 关联上游，不保持长寿命请求 span。

### 2.2 字段策略

| 字段 | Trace 高基数字段 | Metric tag | 说明 |
|---|---:|---:|---|
| requestId、jobId、subscriptionId、tenantId、userId | 允许 | 禁止 | 只记录内部稳定 ID，不记录显示名、邮箱或手机号 |
| batchId、reportId、deliveryId、eventId、notificationId | 允许 | 禁止 | 用于业务链路定位 |
| persisted correlation ID | 允许 | 禁止 | 延迟 job 与原请求/审计记录的关联值 |
| SDK traceId/spanId | SDK 管理 | 禁止自定义 | 不覆盖标准 trace/span 字段 |
| session family | 禁止 | 禁止 | 属于认证敏感标识 |

以下内容在日志、trace 和 metric 中全部禁止：密码、原始 token、refresh/access token、API key、secret、完整 prompt、模型完整输出、工具参数、请求/响应 body、业务 payload 和 SMTP 凭据。

Spring AI 的 `include-error-logging`、`log-prompt`、`log-completion` 已显式关闭。错误只记录异常类型和受控结果，不记录输入输出内容。

## 3. 事件与指标

所有 observation 只使用 `app.component` 和 `app.outcome` 两个低基数 tag。允许的 outcome 为 `success`、`error`、`fallback`、`skipped`、`cancelled`、`rejected`。

| Observation / Actuator metric | 结构化日志 event | 主要关联字段 |
|---|---|---|
| `agentpoc.data.import` | `data.import` | tenantId、batchId |
| `agentpoc.report.generate` | `report.generate` | tenantId、batchId、reportId |
| `agentpoc.report.job.execute` | `report.job.execute` | jobId、subscriptionId、tenantId、creator userId、correlationId、reportId |
| `agentpoc.report.delivery` | `report.delivery` | deliveryId、jobId |
| `agentpoc.report.collaboration.notification` | `report.collaboration.notification` | notificationId、eventId |

Micrometer timer 在 Prometheus 中转换为下划线名称，例如 `agentpoc_report_generate_seconds_count` 和 `agentpoc_report_generate_seconds_sum`。

## 4. 本地诊断

启动后端后执行：

```powershell
Invoke-RestMethod http://localhost:8081/actuator/health
Invoke-RestMethod http://localhost:8081/actuator/metrics
Invoke-RestMethod http://localhost:8081/actuator/metrics/agentpoc.report.generate
(Invoke-WebRequest http://localhost:8081/actuator/prometheus).Content
```

调用任一 API 时可传入受控请求 ID，并检查响应关联头：

```powershell
$response = Invoke-WebRequest `
  -Headers @{ 'X-Request-ID' = 'ops-check-001' } `
  http://localhost:8081/actuator/health
$response.Headers['X-Request-ID']
$response.Headers['X-Trace-ID']
```

健康端点不经过业务关联过滤器时可能没有上述响应头；验证链路时应使用实际 `/api/**` 请求。

## 5. Prometheus 查询基线

按结果统计每秒事件数：

```promql
sum by (app_outcome) (rate(agentpoc_report_job_execute_seconds_count[5m]))
```

报告生成平均耗时：

```promql
sum(rate(agentpoc_report_generate_seconds_sum[5m]))
/
sum(rate(agentpoc_report_generate_seconds_count[5m]))
```

导入 fallback/error 比例：

```promql
sum(rate(agentpoc_data_import_seconds_count{app_outcome=~"fallback|error"}[15m]))
/
sum(rate(agentpoc_data_import_seconds_count[15m]))
```

Dashboard 至少应包含事件吞吐、error/fallback/cancelled 比例、平均耗时，以及 job、delivery、notification 三条执行链路的结果分布。P2-4C 再据此设定告警阈值。

## 6. OTLP 对接

默认不导出 OTLP。Collector 准备完成后，通过环境变量启用：

```powershell
$env:MANAGEMENT_OTLP_TRACING_EXPORT_ENABLED = 'true'
$env:MANAGEMENT_OTLP_TRACING_ENDPOINT = 'http://otel-collector.internal:4318/v1/traces'
$env:MANAGEMENT_TRACING_SAMPLING_PROBABILITY = '0.1'
```

应用使用 OTLP/HTTP。先在测试环境验证 Collector 地址、证书、代理和超时，再发布生产。Collector 不可用时不应影响默认启动；启用导出后需监控 exporter 自身错误和队列压力。

生产如需抓取 Prometheus，显式设置：

```powershell
$env:MANAGEMENT_ENDPOINTS_WEB_EXPOSURE_INCLUDE = 'health,info,prometheus'
```

设置前必须通过内网监听、反向代理鉴权或防火墙限制 `/actuator/**`。应用当前只保证默认生产配置不公开 metrics，不应直接在公网扩大 exposure。

## 7. 采样与保留

* 默认 trace 采样率为 10%。故障排查可短时提高，结束后恢复，避免成本和敏感面扩大。
* 认证失败、安全拒绝和业务 error 仍需保留结构化日志；不要依赖 trace 采样替代安全审计。
* 建议初始保留：trace 7 天、metrics 30 天、运维日志 30 天、安全审计按合规要求单独配置。实际保留由 Collector/后端平台执行，应用不内置保留仓库。
* userId、tenantId 等即使是内部 ID 也按可识别信息处理；仅授予运维最小读取权限，禁止导出到个人设备。

## 8. 故障定位顺序

1. 使用响应 `X-Trace-ID` 查 trace；没有采样结果时，使用 `X-Request-ID`、jobId 或 reportId 查结构化日志。
2. 检查对应 observation 的 `app.outcome` 与耗时，确认是请求失败、fallback、cancelled 还是后台重试。
3. 对延迟 job，先查 job 的持久化 correlation ID，再沿 reportId、deliveryId 或 eventId 查下游。
4. 只能记录受控 ID 和错误码；不要为排障临时打开 prompt、completion、payload 或 token 日志。

## 9. 回滚

观测后端异常或出口压力过大时：

1. 设置 `MANAGEMENT_OTLP_TRACING_EXPORT_ENABLED=false` 并重启应用，停止外部 trace 导出。
2. 将 `MANAGEMENT_TRACING_SAMPLING_PROBABILITY` 恢复为 `0.1`；紧急情况下可临时设为 `0.0`。
3. 将 `MANAGEMENT_ENDPOINTS_WEB_EXPOSURE_INCLUDE` 恢复为生产默认 `health,info`。
4. 保留业务 observation 和关联响应头；它们在无 Collector 时仍可运行，不需要回滚业务代码或数据库。
