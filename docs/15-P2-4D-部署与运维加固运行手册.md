# P2-4D 部署与运维加固运行手册

本手册面向未参与实现的发布、值班和数据库运维人员。它覆盖单体应用镜像、PostgreSQL + PGvector、一次性管理员初始化、发布前备份、认证 smoke、灰度、应用回滚、空库恢复、密钥轮换和事件响应。TLS、外部流量切换、定时调度、持久 secret store 和备份对象存储由目标平台提供。

## 1. 目标与安全边界

* 恢复目标：每日一次全量备份并在每次发布前额外备份，`RPO <= 24h`，`RTO <= 4h`，每月至少一次空库恢复演练。
* PostgreSQL 中的身份、tenant/组织、业务批次、PGvector 知识、报告、订阅/job/投递、审计和模型用量是一个一致恢复单元，不能分别覆盖恢复。
* `/livez` 只判断进程是否存活；只有 `/readyz` 为 `UP` 才能接流量。数据库、Flyway 或知识索引异常必须从流量池移除，但不能触发无休止的 liveness 重启。
* 生产只使用 `prod` profile。关键配置缺失、H2/内存 fallback、非安全 Cookie、非 HTTPS CORS、Flyway 漂移、PGvector/embedding 不一致或共用 AES 密钥都会阻止启动。
* 禁止执行 Flyway `clean`、向下迁移、修改已应用 migration、覆盖非空恢复目标，或把未执行的演练记录成通过。
* 日志和证据中不得出现密码、Bearer/refresh token、API key、AES key、prompt、模型回答、请求/响应正文或业务行。

## 2. 交付物

| 文件 | 用途 |
| --- | --- |
| `Dockerfile` | Node/Maven 多阶段构建，最终使用 JRE、固定非 root UID 运行 |
| `ops/deployment/compose.production.yml` | PGvector 与应用的生产参考拓扑 |
| `ops/deployment/compose.bootstrap.yml` | 仅首次空库启动时挂载一次性管理员密码 |
| `ops/deployment/.env.production.example` | 不含真实值的配置清单 |
| `ops/deployment/operations.py` | `preflight`、`backup`、`restore`、`smoke` 和 `bootstrap-password` |
| `.github/workflows/release-gate.yml` | 完整生产启动、备份、空库恢复和恢复后 smoke 演练 |

Compose 仅把应用端口绑定到 `127.0.0.1`。生产平台应在其前方配置 TLS 终止、访问日志脱敏、限流和流量权重；不得直接把 PostgreSQL 端口发布到公网。

## 3. 发布前准备

运行节点需要 Docker Engine + Compose v2。执行备份/恢复工具的节点还需要 Python 3.11+ 和与 PostgreSQL 16 兼容的 `psql`、`pg_dump`、`pg_restore`。

1. 基于 `ops/deployment/.env.production.example` 创建被 Git 忽略的 `ops/deployment/.env.production`。
2. 在 `ops/deployment/secrets/` 或平台 secret store 中创建数据库密码、两个独立的 32-byte Base64 AES 密钥、embedding API key；首次空库还需要 bootstrap 密码。
3. 将 `APP_VERSION` 设置为不可变镜像版本或提交摘要，不使用 `latest`。
4. `APP_EXCEL_FILE` 必须指向经过审核的真实工作簿。`prod` 不允许内置样例 fallback。
5. CORS 只允许实际 HTTPS origin；embedding 维度保持 `1536`，除非先新增前向迁移并完成全量重建。
6. 确认备份仓库可写、恢复测试库可创建、值班和 DBA 在发布窗口内可响应。

静态检查不连接数据库，也不代表部署成功：

```bash
docker compose --env-file ops/deployment/.env.production \
  -f ops/deployment/compose.production.yml \
  -f ops/deployment/compose.bootstrap.yml \
  config -q
```

生产 secret 应由平台以文件形式挂载，权限限制为应用运行身份可读。不要把 secret 放在镜像、Compose 文件、命令参数、工单正文或仓库 `.env` 中。

## 4. 首次部署与 bootstrap 移除

仅空用户库第一次启动时组合 bootstrap 文件：

```bash
docker compose --env-file ops/deployment/.env.production \
  -f ops/deployment/compose.production.yml \
  -f ops/deployment/compose.bootstrap.yml \
  up -d --build --wait --wait-timeout 300
```

确认 `docker compose ps` 中 PostgreSQL 和应用均 healthy。然后通过安全注入设置以下环境变量，不把值放在命令行：

| 环境变量 | 含义 |
| --- | --- |
| `BOOTSTRAP_USERNAME` | 一次性管理员用户名 |
| `BOOTSTRAP_CURRENT_PASSWORD` | bootstrap 临时密码 |
| `BOOTSTRAP_NEW_PASSWORD` | 符合密码策略的新密码 |

执行强制密码替换：

```bash
python ops/deployment/operations.py bootstrap-password \
  --base-url http://127.0.0.1:8081 \
  --allow-http \
  --evidence artifacts/bootstrap-password.json
```

`--allow-http` 只接受 loopback；经反向代理访问时使用 HTTPS 且不传该参数。密码修改会撤销旧会话。随后停止当前 Compose 项目但保留数据库 volume，再只使用生产文件重启：

```bash
docker compose --env-file ops/deployment/.env.production \
  -f ops/deployment/compose.production.yml \
  -f ops/deployment/compose.bootstrap.yml down

docker compose --env-file ops/deployment/.env.production \
  -f ops/deployment/compose.production.yml \
  up -d --wait --wait-timeout 300
```

从 secret store 撤销并删除 bootstrap 密码，确认新应用容器没有 `APP_AUTH_BOOTSTRAP_USERNAME` 和 bootstrap secret mount。不得删除现有用户以重新触发 bootstrap；初始化逻辑不会覆盖已有账号。

## 5. 发布前检查、备份与 smoke

运维工具通过 `PGHOST`、`PGPORT`、`PGUSER`、`PGDATABASE` 和 `PGPASSWORD` 或 `PGPASSFILE` 连接数据库。优先使用权限受限、短期 `PGPASSFILE`，不要把连接串或密码写入证据。

发布前检查会验证工具版本、V12、Flyway 失败记录、关键表、启用 tenant/membership 和每 tenant 单一 active batch：

```bash
python ops/deployment/operations.py preflight \
  --expected-migration 12 \
  --evidence artifacts/preflight.json
```

先从负载均衡移除应用并停止应用/runner 写入，再创建 PostgreSQL custom-format 备份并立即执行归档列取。当前工具用停写窗口保证 manifest 计数与 dump 一致；若目标平台需要零停机在线备份，应改用平台级 snapshot/PITR 方案并单独验证计数语义。

```bash
python ops/deployment/operations.py backup \
  --output backups/agentpoc-20260816T010000Z.dump \
  --application-version 2026.08.16-1 \
  --evidence artifacts/backup.json

python ops/deployment/operations.py preflight \
  --expected-migration 12 \
  --archive backups/agentpoc-20260816T010000Z.dump \
  --manifest backups/agentpoc-20260816T010000Z.dump.manifest.json \
  --evidence artifacts/backup-inspection.json
```

manifest 只包含时间、应用/迁移版本、归档大小、SHA-256 和非敏感计数。备份文件本身包含生产数据，必须加密传输到独立备份域，并通过访问控制、不可变保留和删除审计保护。

认证 smoke 从只读检查开始，覆盖 liveness/readiness、登录、当前 tenant、Dashboard、数据状态、组织、订阅、模型用量和 SSE/知识。写入型报告草稿只有显式传 `--allow-writes` 才会执行，并只能使用隔离验收 tenant：

```bash
python ops/deployment/operations.py smoke \
  --base-url https://dealer-ai.example.com \
  --tenant-key acceptance \
  --allow-writes \
  --evidence artifacts/smoke.json
```

凭据从 `SMOKE_USERNAME`、`SMOKE_PASSWORD` 读取。证据只保存检查名称、耗时和新建草稿 ID，不保存 token 或响应正文。

## 6. 备份计划与保留

* 每日全量：每天至少一次，在计划停写窗口执行；完成后必须 `pg_restore --list` 且校验 SHA-256。
* 发布前全量：在任何 migration 或应用切流之前生成，并把 manifest 关联到发布工单。
* 建议最低保留：14 份每日、8 份周末、12 份月末备份；法规、合同或数据分类要求更长时以更严格规则为准。
* 备份任务失败、归档不可列取、hash 不一致或备份超出 24 小时时，停止发布并告警。
* 每月至少恢复一份随机选择的备份到新建空库，记录开始/结束时间。超过 4 小时、恢复后 readiness/smoke 失败或任一迁移表计数不一致都算演练失败。
* WAL/PITR 当前不在仓库实现范围。若业务要求 `RPO < 24h`，必须由数据库平台增加 base backup + WAL 归档并单独演练。

## 7. 空库恢复

恢复目标必须是新建且无用户表的数据库；工具会再次检查，但操作人也必须核对目标名称。不要停止源库后原地覆盖。

1. 校验备份 SHA-256、manifest 和 `pg_restore --list`。
2. 在同兼容版本 PostgreSQL/PGvector 实例创建空数据库，例如 `agentpoc_restore_20260816`。
3. 保持 `PGDATABASE` 指向可连接的控制库，执行：

```bash
python ops/deployment/operations.py restore \
  --archive backups/agentpoc-20260816T010000Z.dump \
  --manifest backups/agentpoc-20260816T010000Z.dump.manifest.json \
  --target-database agentpoc_restore_20260816 \
  --confirm-target agentpoc_restore_20260816 \
  --expected-migration 12 \
  --evidence artifacts/restore.json
```

4. 用同一不可变镜像、同一 AES 密钥和新数据库 URL 启动无流量实例。
5. 等待 `/readyz` 为 `UP`，执行只读 smoke，再在隔离 tenant 显式执行写入 smoke。
6. 比较 manifest 与恢复证据中的 tenant、membership、knowledge、report、subscription/job/delivery、audit 和 model usage 计数；启动导入可能产生新的 active batch，必须解释差异并确认每 tenant 仍只有一个 active batch。
7. 记录恢复时长。只有通过 schema/tenant 检查和认证 smoke 后才允许切换数据库连接或流量。

恢复命令采用单事务和 `--exit-on-error`。任何错误都保留新库用于诊断或整库丢弃重建，不能在半恢复库上继续补写。

## 8. 灰度发布与应用回滚

每次发布 manifest 至少记录旧/新镜像摘要、目标 migration、备份 manifest、变更负责人、观察窗口，以及 migration 的回滚分类：

* `application-compatible`：旧应用已验证可在新 schema 上运行，可在观察窗口内只回滚镜像。
* `forward-fix-only`：旧应用与新 schema 不兼容，不允许应用回滚；只能发布前向修复 migration/应用。
* `database-restore-required`：只有经事件指挥和 DBA 审批，才从已验证备份恢复到新库并切换。

标准顺序：

1. 完成 preflight 和发布前备份。
2. 无流量启动新镜像；Flyway 自动 validate/migrate，Hibernate 只做 `validate`。
3. 等待 readiness，执行认证 smoke 和 tenant 隔离回归。
4. 以平台能力逐步切流，例如 5% -> 25% -> 50% -> 100%；每档观察错误率、p95、数据库连接、慢查询、模型 fallback 和 job/delivery 队列。
5. 任一门槛失败立即停止增量流量并保留 trace/request ID。

在 `application-compatible` 窗口内回滚时，只把流量切回旧镜像并保留新 schema，然后重跑 readiness/smoke。禁止运行 Flyway down/clean、删除列、修改已应用 SQL 或恢复数据库来处理普通应用缺陷。窗口结束或执行 contract migration 后，旧镜像应从可回滚列表移除。

## 9. Secret 轮换

| Secret | 安全轮换方式 |
| --- | --- |
| 数据库密码 | 创建新凭据或双密码窗口，更新 secret file，重建应用连接并 smoke，确认旧连接退出后撤销旧凭据 |
| embedding API key | provider 先创建新 key，更新挂载并重启无流量实例，确认知识初始化/readiness 后切流并撤销旧 key |
| bootstrap 密码 | 只在空库首次启动存在；强制改密后立即撤销，不作为日常恢复通道 |
| 模型/通知 AES 主密钥 | 不能直接替换；历史 `tenant_model_configs.secret_ciphertext` 和 `tenant_smtp_configs.password_ciphertext` 会不可读 |

当前 AES provider 只有 `secret_version=1` 的单密钥读取能力，没有在线双读或批量重加密命令。因此主密钥轮换必须先交付并验证一个前向兼容版本：同时持有旧/新 key，写入新版本，按 tenant AAD 解密旧密文后用新 key 重加密，逐行校验，再在计数归零后移除旧 key。数据库备份必须覆盖轮换前后；任何解密失败都停止轮换。不得通过“替换 secret 后观察报错”来测试。

轮换完成的证据只记录密钥版本、处理/失败行数、时间和审批号，不记录密钥、密文或明文。模型 key 与通知 key 必须始终独立。

## 10. 管理员恢复与 tenant 停用

管理员恢复优先使用另一名有效管理员通过现有管理 API 重置临时密码并撤销该用户全部会话；随后用户登录、强制改密并重新验证权限。生产至少维护两名受不同人员控制的有效管理员，并定期验证第二管理员可用。

如果所有管理员凭据都丢失，当前系统故意没有未认证 reset 或重复 bootstrap 后门。停止管理写入并升级为安全事件，只能选择经过评审的临时恢复版本/工具或将最新备份恢复到新库后处置；不得删除 `auth_users`、直接写入明文/未知格式 hash，或复用 bootstrap secret。所有恢复操作需双人审批并保留会话撤销和审计证据。

当前没有 tenant 停用管理 API。需要紧急隔离单个 tenant 时，由 DBA 在事务中锁定目标行，确认唯一 `tenant_key` 后设置 `tenants.enabled=false`，同步 `updated_at` 并递增 `version`；记录工单、操作者、行 ID 和影响时间，不记录业务数据。停用后验证该 tenant 下一请求为 403、其他 tenant 正常、后台 job/delivery 不再执行。恢复前先确认事件原因已消除，再做相反更新和认证 smoke。不要删除 tenant 或级联业务数据。

## 11. 事件响应

| 级别 | 示例 | 第一动作 |
| --- | --- | --- |
| SEV-1 | 跨 tenant 泄露、备份泄露、主密钥泄露、生产数据不可用 | 停止流量/写入，隔离 tenant 或凭据，通知安全/DBA/负责人，保全只含安全标识的证据 |
| SEV-2 | readiness 持续失败、恢复失败、Flyway 漂移、队列持续堆积 | 停止发布，保留实例供诊断，按数据库/迁移/知识/队列 runbook 分流 |
| SEV-3 | 单次 smoke 失败、非关键告警、性能退化未超 SLA | 暂停灰度，关联 request/trace ID，修复后重新跑完整门禁 |

通用步骤：确认影响范围 -> 阻止扩大 -> 保存时间窗/镜像/迁移/备份 hash/request/trace ID -> 选择前向修复、应用回滚或新库恢复 -> 认证 smoke -> 分阶段恢复流量 -> 复盘。不得为排障临时开启 prompt、response body、SQL 参数或 secret 日志。

关联手册：可观测性见 `docs/12-P2-4A-可观测性运行手册.md`，成本异常见 `docs/13-P2-4B-模型用量与成本治理运行手册.md`，健康告警见 `docs/14-P2-4C-健康告警与性能运行手册.md`，tenant 对抗验收见 `docs/11-P2-2D-tenant发布与隔离验收Runbook.md`。

## 12. 证据与完成判定

发布工单必须保存镜像摘要、迁移版本、备份 manifest/hash、preflight/smoke JSON、灰度时间窗、告警状态和回滚分类。CI 的 release gate 保存 JSON 30 天；生产发布与月度恢复证据建议在受控审计存储保留至少 180 天，若组织政策更严格则从其规定。

只有以下条件全部满足才可关闭发布或恢复工单：

* `/readyz` 为 `UP`，认证 smoke 全部通过。
* Flyway 到预期版本、无失败 migration、Hibernate validate 成功。
* tenant/membership 存在，每 tenant 不超过一个 active batch。
* 备份可列取、manifest 与 SHA-256 匹配；恢复演练还需新库检查和恢复后 smoke。
* 证据中抽查不到密码、token、API key、AES key、prompt、响应正文或业务行。
* 实际耗时满足 RTO，备份年龄满足 RPO；不满足时登记失败和改进项，不能标记通过。
