# 前端重构需求

## 目标

把当前演示型聊天页面整理为更适合真实运营分析场景的前端工作台。前端需要稳定消费后端 SSE、清晰展示数据口径和限制、支持安全的模型配置，并让后续重构可以按页面、状态、组件和接口消费拆任务。

## 当前状态

| 主题 | 当前实现 |
| --- | --- |
| 应用形态 | Vue 3 + Vite SPA，无路由，`App.vue` 通过鉴权状态切换 `LoginView` 和 `ChatView` |
| 语言 | JavaScript，不使用 TypeScript |
| 状态管理 | Vue Composition API，无 Vuex/Pinia |
| 页面 | 登录页、聊天工作台 |
| 组件 | `components/chat` 和 `components/layout` 两类组件 |
| API | `src/api` 封装普通 JSON 请求和聊天 SSE |
| 持久化 | 登录 token 在 sessionStorage，locale/model settings/sessionId 在 localStorage，消息不持久化 |
| 渲染 | Markdown、HTML 表格、ECharts、Mermaid、follow-up buttons |
| 测试 | Vitest + Vue Test Utils，测试与模块 co-located |

## 生产化目标

### 用户工作流

* 从“演示聊天窗口”转向“运营分析工作台”。
* 支持清晰的新建会话、清空会话、查看数据源状态、模型连接状态。
* 示例问题从固定演示题库升级为可维护的场景入口。
* 用户能区分系统结论、数据支撑、限制说明和后续追问。

### 状态管理

* 保留 Composition API 的轻量结构，直到有明确复杂度需要引入状态库。
* 明确哪些状态持久化，哪些仅保留在内存。
* 聊天消息是否持久化要作为单独决策，不在本批文档中默认引入。
* SSE 中断、取消、错误、完成状态需要有统一状态机。

### UI 与可解释性

* `analysis_metadata` 是分析口径的权威来源，前端不从 Markdown 正文反推业务口径。
* 图表、表格和 Markdown 渲染必须能降级，不能因为单个图表失败破坏整条回答。
* 缺失数据、样例数据回退、低置信度要有明显但不打断任务流的提示。
* 所有用户可见文案继续走 i18n 字典。

### 安全边界

* 浏览器不应直接持有内部 `APP_API_KEY`。
* 模型 API Key 目前保存在 localStorage，这只是 POC 便利方案，真实项目需要重新评估。
* 登录态、模型设置、会话 ID 的生命周期要在联调和安全文档中统一。

## 待拆任务

| 优先级 | 任务 | 验收 |
| --- | --- | --- |
| P0 | 明确前端页面信息架构 | 有页面列表、入口、状态和空态设计 |
| P0 | 固化 SSE 前端状态机 | 覆盖 idle、sending、streaming、done、error、cancelled |
| P0 | 模型设置安全方案评估 | 明确 localStorage 是否继续使用 |
| P1 | 快捷问题配置治理 | 示例问题来源、场景、语言和维护方式清晰 |
| P1 | 图表渲染降级规范 | ECharts/Mermaid/HTML 表格失败时有降级 UI |
| P1 | 数据源状态提示 | 样例回退、导入失败、低质量数据可见 |
| P2 | 是否引入路由 | 根据页面复杂度再判断，不提前引入 |
| P2 | 是否引入 TypeScript | 根据重构范围和团队成本再判断 |

## 验收标准

* 新增或重构前端功能必须有 co-located Vitest。
* 新 UI 文案必须同时支持 zh/en。
* 新 API 调用必须通过 `frontend/src/api/client.js` 或专用 SSE API。
* 新 storage key 必须集中定义。
* `npm run lint`、`npm run test`、`npm run build` 应作为前端完整门禁。

## 暂不做

* 不在第一轮文档中强行引入路由、Pinia 或 TypeScript。
* 不重做视觉设计稿。
* 不把聊天历史持久化默认为必须项。

## 开放问题

* 真实用户是否需要多会话列表和历史记录？
* 模型配置应由管理员配置，还是继续允许单个用户本地配置？
* 快捷问题未来来自前端常量、后端接口，还是运营可配置后台？
* 图表是否统一用 ECharts，还是继续保留 Mermaid 作为补充？
