# MVP 产品需求文档

## 一句话目标

用可复现的模拟业务数据和 Dashboard MVP，证明经销商 AI 分析助手能帮助集团或区域运营人员快速发现经营问题、理解原因、形成下一步动作。

## 背景

当前项目已经具备聊天、SSE、规则分析、Excel 导入、数据质量提示和题库回归。下一步不应先做完整生产平台，而应先做一个可以让业务用户试看的 MVP。

MVP 的关键问题不是“系统功能是否多”，而是：

* 用户能不能一眼看到经营问题？
* 系统能不能解释这个问题来自哪些数据？
* AI 的回答是不是基于事实，而不是泛泛建议？
* 用户看完之后是否愿意拿真实数据继续试点？

## 目标用户

| 用户 | 核心诉求 | MVP 要满足的价值 |
| --- | --- | --- |
| 集团运营负责人 | 快速掌握整体经营表现和异常门店 | Dashboard 总览、排名、异常预警 |
| 区域经理 | 找到负责区域内的问题门店和改进方向 | 区域/门店对比、漏斗和跟进分析 |
| 门店管理者 | 理解自己为什么落后、下一步做什么 | 数据支撑、原因拆解、行动建议 |
| 项目评审方 | 判断产品是否值得接真实数据试点 | 可复现数据、稳定演示、明确验收 |

## 用户价值

### 价值 1：从“问 AI”变成“看经营状态”

用户不需要先想问题。打开系统后，Dashboard 应该直接呈现目标达成、商机漏斗、线索来源、跟进任务和活动效果。

### 价值 2：从“漂亮回答”变成“可信结论”

每个结论都要能看到数据来源、指标口径、限制说明和置信度。模型可以润色表达，但不能改写 KPI。

### 价值 3：从“样例数据”变成“业务故事”

模拟数据不只是随机数据，而要有明确业务故事：哪些门店落后、为什么落后、哪个来源转化差、哪些活动没有效果、哪些任务积压。

### 价值 4：从“演示一次”变成“可重复验收”

模拟数据生成必须可复现，题库和人工验收脚本必须能重复跑，避免每次演示结果漂移。

## MVP 范围

### 必须包含

| 能力 | 用户价值 | 技术路线 | 验收 |
| --- | --- | --- | --- |
| 模拟业务数据生成 | 没有真实数据也能验证经营场景 | 增强 `SampleWorkbookGenerator`，输出固定种子 XLSX 和场景说明 | 一条命令生成数据，导入后能复现预设洞察 |
| Dashboard 首页 | 用户先看经营状态，不被迫先聊天 | 新增 Dashboard 汇总 API 和前端卡片/图表 | 登录后能看到核心 KPI、排名、漏斗、来源、任务、活动 |
| 数据质量提示 | 用户知道当前数据是否可信 | 复用 `/api/data-status` 和 active batch | 模拟数据、样例回退、缺失值和质量问题可见 |
| 分析入口 | 从问题指标直接追问原因 | Dashboard 卡片触发现有分析场景 | 至少 3 类卡片可进入聊天分析 |
| 规则分析 fallback | 模型不可用时仍能演示 | 复用现有规则引擎和 SSE | 不配置模型也能完成核心分析 |
| KPI 口径说明 | 用户知道结论怎么算出来 | 固化 MVP KPI 分子、分母、过滤条件 | Dashboard 与聊天指标一致 |

### 暂不包含

* 完整数据库替换和生产迁移体系。
* 完整用户账号、角色、组织树和审计后台。
* 自由行动 Agent。
* 完整 RAG 知识库。
* PDF/Word 报告导出。
* 多租户和报告订阅。

## 核心用户流程

### 流程 1：经营总览

1. 用户登录。
2. 进入 Dashboard。
3. 查看目标达成率、商机数、赢单数、线索数、跟进任务和活动数。
4. 系统提示当前使用的是模拟数据、样例数据或真实数据。
5. 用户看到异常门店或低质量数据提示。

成功标准：用户能在 30 秒内说出当前最值得关注的问题。

### 流程 2：从 Dashboard 到 AI 分析

1. 用户点击低达成门店卡片。
2. 系统发起对应分析问题。
3. 后端通过规则分析生成事实锚点。
4. 前端通过 SSE 展示分析步骤、元数据、Markdown 报告和追问。
5. 用户看到原因拆解和行动建议。

成功标准：分析结果包含结论、数据支撑、限制说明和后续问题。

### 流程 3：演示和验收

1. 开发者生成模拟业务数据。
2. 后端导入该数据。
3. 评审方按验收问题逐条查看 Dashboard 和分析结果。
4. 记录哪些洞察有用、哪些指标不清楚、哪些建议不可信。

成功标准：同一份数据、同一批问题可以稳定复现同一组核心洞察。

## 模拟业务数据需求

### 数据规模

MVP 建议保留中型规模，既能演示真实感，又不让本地启动和测试变慢：

| 数据域 | 建议规模 |
| --- | ---: |
| 经销商 | 30-120 家 |
| 月份 | 12 个月 |
| 目标 | 每门店/车型/月一行 |
| 商机 | 20,000-30,000 条 |
| 线索 | 15,000-25,000 条 |
| 任务 | 40,000-60,000 条 |
| 活动 | 1,000-2,400 条 |

### 业务故事

模拟数据至少内置以下故事：

| 故事 | Dashboard 表现 | 分析应能解释 |
| --- | --- | --- |
| 华北某区域目标达成低 | 区域/门店排名靠后 | 目标高、赢单不足、跟进逾期偏多 |
| 某门店线索多但转化低 | 线索量高、转化率低 | 低质量来源占比高、任务未及时跟进 |
| 某活动投入高产出低 | 活动目标达成低 | 实际商机和赢单低于目标，来源转化差 |
| 某车型商机漏斗卡住 | 中间阶段积压 | 高概率商机未及时推进 |
| 某来源自然流量下滑 | 来源趋势下降 | 线索量和转化率同时下降 |
| 数据质量边界 | Dashboard 提示低置信度 | 缺失目标、未知来源、异常概率导致限制 |

### 生成要求

* 使用固定随机种子。
* 输出 XLSX，保持现有 5 个业务 sheet。
* 保留现有导入路径：`APP_EXCEL_PATH` 或 classpath workbook。
* 生成过程输出文件路径和摘要。
* 生成数据要包含正常数据和少量受控异常。
* 同步输出或维护一份场景说明，列出预设问题和预期洞察。

## Dashboard MVP 需求

### 页面结构

| 区域 | 内容 |
| --- | --- |
| 顶部概览 | 目标达成率、商机数、赢单数、线索数、任务数、活动数 |
| 数据状态 | 当前数据源、批次、导入时间、质量问题、是否模拟数据 |
| 目标达成 | 低达成门店排行、区域对比 |
| 商机漏斗 | 阶段分布、转化率、高概率商机 |
| 线索来源 | 来源占比、来源转化率 |
| 跟进任务 | 完成率、逾期率、积压门店 |
| 活动效果 | 目标与实际对比、活动排名 |
| 分析入口 | 每个模块提供 1-2 个可点击分析问题 |

### 状态要求

* Loading：卡片骨架或轻量加载态。
* Empty：说明没有匹配数据。
* Error：说明接口失败，允许刷新或继续使用聊天。
* Low confidence：说明样本不足或数据质量问题。
* Simulated data：明确提示当前是模拟数据，不代表真实经营结果。

## 技术路线和用户价值映射

| 技术路线 | 对应用户价值 | 为什么先做 |
| --- | --- | --- |
| 固定种子模拟数据 | 可重复演示和验收 | 真实数据接入前也能证明产品方向 |
| active batch | 用户知道当前分析基于哪批数据 | 避免多次导入混杂 |
| 数据质量报告 | 用户知道结论可信度 | 避免 AI 掩盖数据问题 |
| 统一 KPI 口径 | Dashboard 和分析回答一致 | 建立信任 |
| Dashboard 首屏 | 用户不用先学会提问 | 降低使用门槛 |
| 规则分析 fallback | 模型不可用时仍能工作 | 降低外部模型依赖 |
| SSE 分析步骤 | 用户能看到分析过程 | 提高可解释性 |

## 成功指标

| 指标 | MVP 目标 |
| --- | --- |
| 首屏理解时间 | 业务用户 30 秒内能说出 1 个经营问题 |
| 演示稳定性 | 同一数据和问题可复现核心洞察 |
| 指标一致性 | Dashboard 和聊天分析核心 KPI 一致 |
| 可解释性 | 每个分析回答包含口径、来源、限制 |
| 数据质量可见性 | 模拟数据和质量问题不会被隐藏 |
| 试点意愿 | 评审方愿意提供真实或脱敏真实数据继续试点 |

## 验收问题示例

| 问题 | 期望 |
| --- | --- |
| 哪些经销商目标达成率最低？ | 返回低达成门店、达成率、分子分母、限制 |
| 哪个线索来源转化率最差？ | 返回来源排名、转化率和样本量 |
| 哪些门店跟进任务积压严重？ | 返回逾期/待处理任务和门店 |
| 哪些活动投入高但产出低？ | 返回活动目标和实际产出对比 |
| 当前数据质量有什么问题？ | 返回缺失、跳过、未知分类、异常值摘要 |

## 验收标准

* [x] 能生成 MVP 模拟业务数据工作簿。
* [x] 后端能导入该工作簿并暴露数据状态。
* [x] Dashboard 能展示至少 5 类核心经营指标。
* [x] Dashboard 卡片能触发至少 3 类分析问题。
* [x] 未配置外部模型时，规则路径仍能完成核心分析。
* [x] Dashboard 和聊天分析的核心 KPI 一致。
* [x] 数据质量和模拟数据状态对用户可见。
* [ ] PRD 中的验收问题可以用于人工演示。

## 实施状态（2026-07-31）

* 后端新增 `GET /api/dashboard`，返回数据状态、经营概览、目标达成、商机漏斗、线索来源、跟进任务和活动效果。

## 后续演进

MVP 验证通过后，再进入后续阶段：

1. 接入持久化数据库和迁移工具。
2. 接真实或脱敏真实数据。
3. 引入受控 Agent。
4. 建设 RAG 知识库。
5. 自动生成报告并支持导出。
6. 建立完整用户权限、审计和多租户。

## 决策记录

**决策**：P0 收敛为 MVP，不再把完整数据库替换、完整权限、Agent、RAG 和报告中心全部放入 P0。

**原因**：当前最重要的是验证用户价值。模拟业务数据和 Dashboard 能最快证明产品是否解决真实经营分析问题。

**影响**：P0 更小、更容易验收；P1/P2 仍保留生产化路线，但必须建立在 MVP 反馈之上。
