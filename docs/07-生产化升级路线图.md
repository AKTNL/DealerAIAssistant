# 生产化升级路线图

## 目标

把经销商 AI 分析助手从当前 POC 升级为可真实试点、可持续迭代的经营分析产品。当前路线先收敛到 MVP：用可复现的模拟业务数据、可信 Dashboard 和可解释分析链路证明用户价值，再逐步补数据库生产化、Agent、RAG、自动报告和完整权限。

本路线图作为后续拆任务和验收的总纲。具体实现前仍需回到对应专题文档确认细节：

* `08-MVP产品需求文档.md`：MVP 用户价值、功能范围、技术路线和验收。
* `06-数据导入MVP实施说明.md`：现有 MVP 样例数据生成、导入和 active batch 行为。
* `03-数据重构需求.md`：数据源、字段、缺失值、质量报告、迁移。
* `02-后端重构需求.md`：API、服务边界、AI/规则链路、安全配置。
* `01-前端重构需求.md`：Dashboard、工作台、SSE 状态、前端体验。
* `04-联调方案.md`：本地、测试、模型服务和数据联调。
* `05-测试验收方案.md`：自动化测试、准确率题库、人工验收。

## 当前判断

当前项目已经具备可运行的端到端能力：前端聊天工作台、后端规则分析、SSE、Excel 导入、数据质量状态、可选外部模型润色、自动化测试和 CI。它的价值不在于“会聊天”，而在于已经形成了一个可复现的规则分析底座。

现在不应该把 P0 做成“大生产平台”。如果一开始同时做完整架构重构、持久化数据库、完整权限、Agent、RAG、报告中心，风险会变成工程量很大但业务价值还没有被验证。

新的优先级判断：

* P0 先做 MVP：模拟业务数据生成、MVP PRD、最小业务模型、Dashboard 首版、现有分析链路串联。
* P1 做工程化和智能化：持久化数据库、迁移、受控 Agent、RAG 知识库、自动报告。
* P2 做产品化：完整用户权限、多租户、订阅推送、运维和成本治理。

## 总体原则

1. 先用高质量模拟数据证明用户价值，再接真实数据。
2. Dashboard 是第一真实产品界面，聊天是分析入口之一，不是唯一入口。
3. 规则引擎和指标服务负责事实，模型负责解释、归纳、追问和报告表达。
4. 结构化 KPI 查数据库或结构化数据服务，不放进 RAG；RAG 放业务制度、口径说明、SOP、产品知识和非结构化资料。
5. MVP 可以暂缓完整权限，但数据范围概念要提前保留，避免后续 Dashboard 和 Agent 返工。
6. 每个阶段都要保留可回归验收：自动化测试、准确率题库、人工业务抽查。

## MVP 架构

MVP 推荐继续采用模块化单体，不急着拆微服务，也不急着替换全部基础设施。

```text
模拟业务数据生成
        |
        v
Excel / Active Batch Import
        |
        v
当前结构化数据层
        |
        +-- 指标计算
        +-- 数据质量状态
        +-- 规则分析 fallback
        |
        v
Dashboard MVP + Chat Workspace
        |
        v
用户验证：看板是否可信、洞察是否有用、报告是否值得继续做
```

MVP 的关键不是“底层技术一步到位”，而是形成一个可以演示、可以验收、可以反复跑的业务闭环：

```text
生成模拟业务数据 -> 导入并展示数据质量 -> Dashboard 查看经营状态
-> 点击问题进入分析 -> 输出可解释结论 -> 收集用户反馈
```

## 模块边界

| 模块 | MVP 职责 | 后续扩展 |
| --- | --- | --- |
| 模拟数据 | 生成有业务故事的可复现样例数据 | 生成更多场景、自动标准答案、脱敏真实数据回放 |
| 数据接入 | 复用现有 Excel 导入和 active batch | 接真实 CRM/DMS/BI、持久化 batch 和质量问题 |
| 指标服务 | 统一核心 KPI 计算和 Dashboard 数据 | 独立 KPI definition、更多筛选和趋势 |
| Dashboard | 展示核心经营状态、异常和分析入口 | 多页面、下钻、报告订阅 |
| 规则分析 | 生成可复现事实锚点和分析报告 | 注册为 Agent 工具 |
| Agent 编排 | MVP 不做完整 Agent，只保留后续接口方向 | P1 实现受控工具调用 |
| RAG 知识库 | MVP 不做完整 RAG，只定义知识范围 | P1 接入 SOP、政策、口径说明 |
| 报告生成 | MVP 可先做报告草稿文档结构 | P1 实现自动生成和导出 |
| 权限审计 | MVP 保留默认 scope 概念 | P2 做完整用户、角色、审计 |

## P0：MVP 验证

P0 的目标是快速做出一个能被业务用户试看的最小可用版本。完成后，用户应该能回答三个问题：

* 这个 Dashboard 是否能反映经销商经营问题？
* AI 分析是否基于数据，而不是空泛建议？
* 这套产品是否值得接入真实业务数据继续试点？

### 1. MVP PRD

目标：把用户价值和技术路线扣在一起，避免后续只按技术清单推进。

交付：

* `08-MVP产品需求文档.md`。
* 明确目标用户、核心问题、用户价值、MVP 范围、验收标准。
* 建立“用户价值 -> 产品能力 -> 技术实现 -> 验收方式”的映射。

验收：

* PRD 能解释为什么先做 Dashboard，而不是先做完整 Agent。
* PRD 能解释为什么先做模拟业务数据，而不是马上接真实数据。
* 后续任务可以从 PRD 拆出实现项。

### 2. 模拟业务数据生成

目标：生成一套比普通样例数据更接近真实经营场景的可复现数据，用于 Dashboard、规则分析、题库回归和演示。

现有基础：

* 已有 `SampleWorkbookGenerator` 可生成中型 MVP 工作簿。
* 已有 `06-数据导入MVP实施说明.md` 记录生成命令、输出路径和 active batch 行为。

MVP 需要增强的方向：

* 数据不只是随机行，而要包含可讲述的业务故事。
* 至少覆盖 12 个月、多个区域、多个经销商、多个车型。
* 内置几类经营模式：
  * 高目标低达成门店。
  * 高线索低转化门店。
  * 商机跟进逾期导致赢单差的门店。
  * 活动投入高但产出低的活动。
  * 线索来源结构变化导致转化下滑。
  * 数据缺失、未知分类、异常概率等质量边界。
* 固定随机种子，保证每次生成结果可复现。
* 输出一份场景说明，列出预期洞察和可提问问题。

验收：

* 一条命令可以生成 MVP 工作簿。
* 后端能用该工作簿启动导入。
* Dashboard 能显示至少 5 类核心经营指标。
* 准确率题库或人工验收问题能命中模拟数据里的预设业务故事。
* 数据质量问题能在前端可见。

### 3. 最小业务数据模型和 KPI 口径

目标：先不做完整数据平台，但要把 MVP 需要的业务对象和指标口径固定下来。

MVP 业务对象：

* 经销商：编码、名称、城市、区域、集团。
* 目标：年月、车型、目标量、实际赢单、创建商机数。
* 商机：阶段、线索来源、购车周期、车型、概率、时间。
* 线索：来源、状态、是否转化、车型、时间。
* 任务：状态、创建时间、关联商机。
* 活动：类型、目标、实际商机、赢单、线索。

MVP KPI：

* 目标达成率。
* 商机转化率。
* 漏斗阶段分布。
* 线索来源转化。
* 跟进任务完成率和逾期率。
* 活动目标达成。
* 经销商排名和异常门店。

验收：

* 每个 KPI 都能回答：分子是什么、分母是什么、哪些行被排除。
* `null`、真实 `0`、未知、未分配、跳过行的规则明确。
* Dashboard 和聊天分析共用同一套口径。

### 4. Dashboard MVP

目标：让用户不用先提问，也能直接看到经营状态和重点问题。

首版建议包含：

* 经营概览：目标达成率、商机数、赢单数、线索数、跟进任务、活动数。
* 目标达成：低达成门店排行。
* 商机漏斗：阶段分布和转化率。
* 线索来源：来源占比和转化率。
* 销售跟进：逾期任务和积压门店。
* 活动效果：活动目标与实际产出。
* 数据状态：当前数据源、批次、样例/模拟数据提示、质量问题。
* 分析入口：从卡片发起预置分析问题。

验收：

* 登录后优先进入 Dashboard 或清晰看到 Dashboard 入口。
* Dashboard 所有核心卡片都有 loading、empty、error 和数据质量提示。
* Dashboard 指标与聊天回答一致。
* 每个卡片都能解释“为什么这个指标对经营有用”。

实施状态（2026-07-31）：

* 已新增 `GET /api/dashboard` 汇总 API，并同步 OpenAPI。
* 已实现登录后默认进入 Dashboard 的前端首版，覆盖数据状态、核心 KPI、目标达成、商机漏斗、线索来源、跟进任务和活动效果。
* 已补齐 Dashboard loading、empty、error、低置信度、模拟数据和 active batch 可见状态。
* 已补 Dashboard service/controller/filter、前端 API/composable/view 和 ChatView 回归测试。

### 5. 现有分析链路串联

目标：复用已有规则分析和 SSE，不在 P0 重新实现完整 Agent。

交付：

* Dashboard 卡片可以触发现有分析场景。
* 分析结果继续显示口径、数据来源、限制和置信度。
* 模型未配置时仍能用规则路径回答。

验收：

* 用户能从 Dashboard 进入至少 3 类分析问题。
* 模型不可用时不影响 MVP 主流程。
* 分析结论能追溯到模拟数据和 KPI 口径。

实施状态（2026-07-31）：

* Dashboard KPI 卡片和模块按钮已复用现有 `submitPrompt(...)`，不会引入第二套分析传输。
* 默认模型未配置时，规则分析 fallback 仍通过现有聊天/SSE 链路工作。
* Dashboard 与聊天共享 active batch 和核心业务实体，后续如新增 KPI 口径需同步更新回归测试。

### P0 暂不做

* 不做完整数据库替换和迁移体系。
* 不做完整账号、角色、组织树和审计后台。
* 不做自由行动 Agent。
* 不做完整 RAG 知识库。
* 不做 PDF/Word 报告导出。
* 不重写全部前端架构。

## P1：工程化和智能化

P1 的目标是在 MVP 用户价值被验证后，把底座变得更接近真实试点环境，并开始增强 AI 分析能力。

### 1. 持久化数据库和迁移

目标：把 H2 内存库升级为可持久化、可迁移、可隔离的数据库。

推荐方向：

* 真实环境使用 PostgreSQL 或 MySQL。
* 引入 Flyway 或 Liquibase 管理 schema。
* 关闭生产环境 `ddl-auto:update`。
* 为导入批次、数据版本、来源、质量问题建立持久化表。
* 保留 Excel 导入作为本地 demo、模拟数据和临时导入路径。

验收：

* 本地能用持久化数据库启动。
* schema 由迁移脚本创建。
* 同一业务 ID 可以在不同 import batch 中共存。
* 所有用户可见查询默认读取当前 active batch。

### 2. 架构模块化

目标：从 POC 代码形态整理为模块化单体。

建议拆分逻辑模块：

* `auth`：登录、session、用户范围上下文。
* `organization`：集团、区域、城市、经销商、门店范围。
* `data-import`：文件导入、真实源同步、批次、质量报告。
* `metrics`：KPI 定义、聚合、详情查询。
* `dashboard`：Dashboard 汇总 API。
* `analytics`：规则分析、意图识别、分析计划、事实锚点。
* `agent`：工具编排、会话上下文、模型调用。
* `reporting`：报告模板、生成、导出、历史。
* `knowledge`：RAG 文档、切片、索引、检索。

验收：

* 有模块边界文档和包结构规划。
* Controller 不承载业务逻辑。
* ChatService 的职责被规划为编排、规则、模型、SSE、守卫等子模块。
* 新功能能明确归属到某个模块。

### 3. 受控 Agent 系统

目标：实现受控 Agent，而不是自由行动 Agent。

Agent 首版工具建议：

| 工具 | 用途 |
| --- | --- |
| `getDashboardSummary` | 获取当前范围核心经营摘要 |
| `queryMetric` | 查询单个 KPI 或排名 |
| `queryDetails` | 拉取分页明细 |
| `runScenarioAnalysis` | 调用现有规则分析场景 |
| `retrieveKnowledge` | 检索业务知识库 |
| `generateReportDraft` | 生成报告草稿 |

实施状态（2026-08-09）：

* P1-3 首版已接入 `getDashboardSummary`、`queryMetric`、`queryDetails`、`runScenarioAnalysis` 四个只读业务工具；`retrieveKnowledge` 和 `generateReportDraft` 留给后续 RAG/报告阶段，不在当前运行时注册。
* 每个已认证经营分析请求只获得上述固定白名单，最多执行 4 次工具调用；明细查询单页最多 50 条，并校验指标/明细类型、筛选字段、排序和分页参数。
* scope 当前明确为“token subject 拥有当前 session + 只读 active import batch”。组织、角色和多租户隔离仍属于 P2，不能把当前实现表述为完整权限系统。
* 同步聊天与 SSE 共用受控 callbacks；遗留低层查询工具不挂载到 Agent 链路。模型创建/调用、工具执行、预算或回复守卫失败时继续返回规则分析报告。
* 服务端 trace 仅记录 traceId、工具名、状态和安全原因，不记录 token、subject、用户消息、工具参数或业务明细；现有 HTTP DTO 和 SSE 协议未改变。

验收：

* Agent 不能绕过权限或 scope。
* Agent 不直接拼 SQL。
* 模型不可用时仍可返回规则分析结果。
* 回答包含结论、数据支撑、限制、置信度和追问。

### 4. RAG 知识库

目标：让 AI 理解业务背景、术语、SOP 和政策，但不把结构化经营数据塞进向量库。

适合进入 RAG 的内容：

* KPI 口径解释。
* 销售运营 SOP。
* 经销商管理政策。
* 产品、车型、活动规则。
* 常见问题处理流程。
* 报告写作模板和表达规范。

不适合进入 RAG 的内容：

* 每日商机明细。
* 线索、任务、目标、活动结构化数据。
* 需要精确聚合计算的 KPI。
* 权限敏感且未做隔离的数据。

验收：

* 检索结果带来源文档和版本。
* RAG 结果只作为解释上下文，不改写 KPI。
* 无命中文档时明确说明。

### 5. 自动报告生成

目标：基于 Dashboard 和指标服务生成可交付报告。

报告类型建议：

* 日报：昨日/当日经营概况、异常门店、待跟进事项。
* 周报：趋势、排名、改善建议、活动复盘。
* 月报：目标达成、区域对标、线索质量、销售效率。
* 专题报告：某区域、某门店、某车型、某活动分析。

验收：

* 报告可从 Dashboard 或聊天分析触发。
* 报告生成使用同一套指标服务。
* 报告可导出 Markdown，后续扩展 PDF/Word。
* 报告记录数据批次、生成时间、scope、模型和 prompt 版本。

## P2：产品化增强

P2 的目标是把试点产品变成可运营、可扩展、可审计的平台。

### 1. 完整用户权限

能力范围：

* 用户账号。
* 角色和权限。
* 组织树。
* 门店、区域、集团数据范围。
* API 权限和页面权限。
* 审计日志。
* token 生命周期、刷新、退出、禁用。

验收：

* 不同角色只能看到自己的数据范围。
* 权限变更后立即影响后端查询。
* 所有敏感操作有审计记录。

### 2. 多租户和数据隔离

能力范围：

* 多集团或多品牌隔离。
* 租户级模型配置。
* 租户级知识库。
* 租户级数据导入批次。
* 租户级报告和历史。

验收：

* 任一 API 都不能跨租户读取数据。
* 数据库索引和查询默认包含 tenant/scope 条件。

### 3. 订阅、推送和协作

能力范围：

* 报告订阅。
* 定时生成。
* 邮件、企业微信、钉钉或飞书推送。
* 报告评论和处理状态。
* 异常任务派发。

验收：

* 用户能订阅固定范围和频率的报告。
* 失败任务可重试、可查看原因。

### 4. 运维和成本治理

能力范围：

* 结构化日志。
* traceId 全链路追踪。
* 模型调用次数、耗时、token、费用统计。
* 数据导入耗时和失败告警。
* Dashboard 慢查询监控。
* 健康检查和发布回滚。

验收：

* 线上问题能按 traceId 定位到请求、数据批次、模型调用和报告。
* 模型成本可按用户、租户、场景统计。

## 推荐实施顺序

### 阶段 0：MVP PRD 和演示故事

交付：

* MVP PRD 评审通过。
* 明确第一批目标用户：集团运营或区域经理。
* 明确第一批问题清单。
* 明确模拟数据要支撑的业务故事。

建议任务：

* 完成 `08-MVP产品需求文档.md`。
* 设计模拟业务数据故事线。
* 选择 Dashboard MVP 信息架构。

### 阶段 1：模拟业务数据生成

交付：

* 可复现的 MVP 工作簿。
* 数据故事说明。
* 质量边界样本。
* 问题题库和预期洞察。

建议任务：

## 里程碑定义

| 里程碑 | 标准 |
| --- | --- |
| M1 MVP 故事可信 | 模拟数据能支撑明确业务故事和验收问题 |
| M2 Dashboard 可用 | 业务用户能不通过聊天完成核心经营查看 |
| M3 分析可解释 | AI/规则分析能解释 Dashboard 异常，且可追溯数据口径 |
| M4 工程可试点 | 持久化、迁移、真实数据接入和环境配置具备试点条件 |
| M5 AI 可控 | Agent 只能调用受控工具，回答可追溯，模型失败可降级 |
| M6 产品可运营 | 用户、权限、审计、监控、订阅和多租户具备平台化能力 |

## 风险和处理策略

| 风险 | 表现 | 处理策略 |
| --- | --- | --- |
| P0 太大导致迟迟不可用 | 工程清单很多，但业务用户看不到价值 | P0 缩小到 MVP，先用模拟数据和 Dashboard 验证 |
| 模拟数据太随机 | 看板有数但没有业务故事 | 预设场景、异常门店、预期洞察和验收题 |
| 先做 Agent 导致幻觉 | AI 看似聪明但 KPI 不可信 | P0 先固化指标和事实锚点 |
| Dashboard 指标与聊天指标不一致 | 用户看到两个答案 | 共用同一指标口径和回归测试 |
| 真实数据质量差 | 接入后结论误导 | P0 先用质量边界样本训练前后端提示 |
| 权限后补导致返工 | 数据表和 API 没有 scope | MVP 保留 scope 概念，上线完整权限放 P2 |
| RAG 被误用为数据仓库 | 精确数值无法保证 | 结构化经营数据只查数据库或结构化指标服务 |

## 暂不做

* 不在 MVP 拆微服务。
* 不在 MVP 强制替换完整数据库体系。
* 不在 MVP 引入自由行动 Agent。
* 不在 MVP 建完整 RAG 知识库。
* 不在 MVP 做完整账号、权限和组织树后台。
* 不把结构化经营明细放进向量库作为主查询路径。
* 不为了 Dashboard 立即强制引入复杂前端状态库。
* 不用人工验收替代自动化回归。

## 每次升级任务的通用验收

后续每个升级任务至少回答：

* 是否服务了 MVP 用户价值？
* 是否改变了数据口径？
* 是否影响 Dashboard 和聊天的一致性？
* 是否影响模拟数据故事和验收题？
* 是否影响权限范围或未来权限模型？
* 是否需要更新 OpenAPI、SSE 契约或文档？
* 是否需要补准确率题库？
* 是否跑过对应质量门禁？

推荐质量门禁：

```bash
cd frontend
npm run lint
npm run test
npm run build

cd ../backend
mvn "-Dfrontend.skip=true" pmd:check
mvn "-Dfrontend.skip=true" test
```

如果只改文档，可以不跑完整测试，但必须确认没有修改代码行为。

## 下一步建议

下一批任务建议按 MVP 顺序拆：

1. 跑通 MVP 试点验收脚本，验证用户是否能从 Dashboard 发现问题。
2. 增强模拟业务数据生成器，让数据带业务故事。
3. 补人工演示脚本和反馈表，记录哪些洞察有用、哪些口径不清晰。
4. 基于试点反馈决定 P1 的筛选、趋势、下钻、报告草稿和真实数据接入优先级。

这条路线的核心判断是：先交付一个可信的经营分析 MVP，再让数据库、Agent、RAG、报告和权限逐步成为放大器。这样升级出来的项目不会只是更华丽的 Demo，而是能被业务人员真实使用并愿意继续试点的工具。
