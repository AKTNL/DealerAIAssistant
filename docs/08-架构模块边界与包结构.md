# 架构模块边界与包结构

本文记录 P1-2 的模块化单体规划，并同步 P1-3 受控 Agent 与 P1-4 RAG 知识库运行时边界。当前应用仍以一个 Spring Boot 进程部署；模块边界先通过业务分包、公开应用入口和回归测试建立，再按小切片迁移遗留代码。

## 模块地图

| --- | --- | --- | --- |
| `auth` | 登录、session、token、用户范围上下文 | `AuthController`、认证与 session 服务 | 遗留 `controller`/`service`，待迁移 |
| `organization` | 集团、区域、城市、经销商、门店范围 | dealer/organization 实体与端口 | 预留边界 |

## 推荐包结构

新模块按业务能力作为一级包，模块内部按职责分层。Java 包名使用 `dataimport`，因为包名不能包含路线图中的连字符。

```text
com.brand.agentpoc
├── auth/
│   ├── controller/          # HTTP 适配
│   ├── application/         # 登录/session 用例
│   ├── domain/              # 认证策略与范围模型
│   └── infrastructure/     # token、配置、持久化适配
├── dataimport/
│   ├── controller/
│   ├── application/
│   ├── domain/
│   └── infrastructure/
├── metrics/
├── dashboard/
├── analytics/
├── agent/
│   ├── controller/          # 后续迁移 ChatController
│   ├── application/         # 受控工具门面、scope port；后续承接 Chat orchestration
│   ├── domain/              # 工具白名单、执行预算、请求 scope、最小 trace
│   ├── infrastructure/     # Spring AI callbacks、scope verifier；后续承接模型/SSE/memory adapters
│   └── ChatReplyGuard.java  # 回复结构和事实一致性守卫
├── reporting/
├── knowledge/
│   ├── application/         # 检索/索引 ports、用例、确定性回答 composer
│   ├── domain/              # 文档、切片、query、hit 和 no-match 合同
│   └── infrastructure/     # classpath catalog、内存索引、PGvector、启动摄取
├── config/                  # 过渡期共享 Spring 配置与 filters
├── dto/                     # 过渡期共享 API records，逐模块收敛
├── entity/                  # 过渡期 JPA entities，避免本任务改映射
└── repository/              # 过渡期 Spring Data repositories
```

## 依赖方向

```text
controller -> application -> domain
                         -> ports
infrastructure -> ports / domain

dashboard -> metrics / dataimport / organization application ports
analytics -> metrics / organization application ports
agent -> analytics application ports / knowledge application ports / auth scope ports
reporting -> analytics application ports
knowledge -> organization scope ports
```

约束如下：

1. Controller 只做参数校验、HTTP/SSE 协议适配、认证上下文读取和响应映射；不直接访问 repository，不编排业务流程。
2. 模块间只依赖对方公开的 application service 或 port，不直接引用对方的 repository、entity 或内部实现。
3. `domain` 不依赖 Spring MVC、Servlet、数据库实现或模型 SDK。
4. `infrastructure` 负责数据库、文件、模型和 SSE 等外部适配；适配细节不向 Controller 泄漏。
5. 根 `service`、`ai`、`dto`、`entity`、`repository` 是迁移过渡区；新功能不得因为方便而继续扩展这些包。
6. 每次迁移必须保持现有 API、SSE 事件顺序/字段、active batch 语义和相关回归测试。

## P1-3 受控 Agent 运行时

受控 Agent 采用“业务级工具门面 + 模型工具选择 + 统一策略校验 + 规则分析 fallback”，不引入自由行动框架。同步聊天和 SSE 共用同一套 request-scoped callbacks：

```text
ChatController（认证并确认 session ownership）
  -> AgentRequestScope
  -> ChatService（先生成规则分析事实锚点）
  -> ControlledAgentToolCallbacks（每请求只发布固定白名单）
  -> AgentExecutionContext（scope、allowlist、预算、最小 trace）
  -> ControlledAgentToolService（参数、分页和排序校验）
  -> DashboardService / AnalyticsApiService / RuleBasedAnalyticsService
  -> active import batch 数据
```

当前注册六个只读业务工具：

| 工具 | 公开能力 | 主要约束 |
| --- | --- | --- |
| `getDashboardSummary` | 获取当前经营摘要 | 复用 `DashboardService`，只读 active batch |
| `queryMetric` | 查询目标、商机、线索、任务或活动指标 | 指标类型和筛选字段固定，不接收 SQL、repository、dataset 或 batch 标识 |
| `queryDetails` | 查询五类业务明细 | 一页最多 50 条，页码、排序字段、排序方向和筛选字段均校验 |
| `runScenarioAnalysis` | 调用现有确定性分析计划 | 问题长度和语言受限，返回事实锚点、限制、置信度和规则 fallback |
| `retrieveKnowledge` | 检索 KPI 口径、SOP、政策和产品/活动规则 | 只调用 knowledge application port；Top-K 受限，命中返回来源、版本、章节、chunk 和 score，无命中显式返回 |
| `generateReportDraft` | 生成当前 active batch 的日报、周报、月报或专题 Markdown 草稿 | 只调用 reporting application port；scope 仅允许 `GLOBAL`，不写业务数据，不导出 PDF/Word |

每个模型请求最多执行 4 次工具调用。工具执行前重新验证 token subject 是否仍拥有当前 session，并要求 `activeBatchOnly=true`；当前边界不等同于完整组织、角色或多租户授权。trace 只记录随机 `traceId`、工具名、成功/拒绝/失败状态和安全原因，不记录 token、subject、用户消息、工具参数或明细结果。

遗留 `ai` 包中的 `searchDealers`、`queryOpportunities` 等低层 `@Tool` 为兼容代码，不能注册到聊天 Agent 链路。模型不可用、模型或工具调用失败、预算超限、scope 校验拒绝、或最终回答未通过 `ChatReplyGuard` 时，分析请求必须返回 `RuleBasedAnalyticsService` 生成的规则报告；知识单问必须返回 `KnowledgeAnswerComposer` 的确定性带引用/no-match 回答。HTTP DTO 和 SSE 事件协议保持不变。

### P1-5 自动报告

报告链路采用“active batch 指标快照 + reporting application port + 双存储 adapter”的边界：

```text
DashboardService / ImportBatchService
  -> reporting.application.ReportService
       -> ReportMarkdownRenderer
       -> ReportDraftStore
            ├── InMemoryReportDraftStore (default/local/test)
            └── JdbcReportDraftStore (prod + Flyway V3)
  -> ReportController / ControlledAgentToolService.generateReportDraft
  -> sync / SSE ChatService
```

报告草稿合同固定包含 `reportType`、`language`、`markdown`、`generatedAt`、`importBatchId`、`scope`、`model` 和 `promptVersion`。报告只读取结构化 Dashboard 指标；趋势、原因、组织范围或未提供的历史事实不得由报告生成器推断。聊天中明确要求日报/周报/月报/专题报告时，同步和 SSE 均可直接生成并记录确定性 Markdown 草稿。

## P1-4 RAG 知识库

知识链路采用“框架中立合同 + 双检索 adapter + 受控 Agent 工具”的边界：

```text
classpath knowledge/catalog.json + reviewed Markdown
  -> ClasspathKnowledgeCatalogLoader（manifest/资源校验）
  -> KnowledgeDocumentChunker（标题优先、确定性切片、稳定 chunk id）
  -> KnowledgeBootstrap（按 bundled catalog 替换版本）
  -> KnowledgeIndex
       ├── InMemoryKnowledgeIndex（default/local/test，确定性词法检索）
       └── PgVectorKnowledgeIndex（prod，Spring AI PgVectorStore + EmbeddingModel）
  -> KnowledgeService（query/Top-K 校验、稳定 KnowledgeSearchResult）
  -> ControlledAgentToolService.retrieveKnowledge
  -> sync / SSE ChatService
```

`knowledge.domain` 与 `knowledge.application` 不引用 Spring AI、JDBC、Spring Resource 或模型 SDK。`agent` 只能依赖 `KnowledgeService`/`KnowledgeAnswerComposer`，不能直接访问 `VectorStore`、catalog loader 或数据库。命中合同包含 `documentId`、`source`、`version`、`section`、`chunkId`、`excerpt` 和 `score`；无命中使用显式 `noMatch`，不能让模型凭常识补写政策。

默认 profile 选择内存 adapter，使 H2 开发和自动化测试无需 embedding 服务。`prod` 明确选择 PGvector，Flyway 在独立 PostgreSQL location 创建 `vector` 扩展、文本主键向量表和 HNSW cosine 索引；缺少 `EmbeddingModel`、扩展、迁移或连接时必须启动失败，不能静默切回内存。embedding 维度必须同时匹配模型、`APP_KNOWLEDGE_EMBEDDING_DIMENSIONS` 与迁移表结构，变化时通过前向迁移和重新索引处理。

当前聊天模型、`@Tool` 和 request-scoped callbacks 已使用 Spring AI 1.0，且它已覆盖本阶段的 PGvector/embedding 能力，因此 P1-4 继续复用 Spring AI，避免并存两套模型工具抽象。若后续离线检索评测、供应商兼容或运维约束证明有必要，可新增或替换 LangChain4j infrastructure adapter；knowledge domain/application 与 Agent 工具合同不变。

## ChatService 拆分路线

| 当前职责 | 目标模块/组件 | 本次状态 |
| --- | --- | --- |
| 聊天同步与流式请求编排 | `agent.application.ChatOrchestrator` | 仅规划 |
| 业务范围/未知实体判断 | `agent.application.ChatScopePolicy` | 仅规划 |
| 规则分析调用与事实锚点 | `analytics.application.AnalyticsOrchestrator` | 仅规划 |
| 模型连接与 prompt | `agent.infrastructure.ModelGateway` / `ai` adapter | `ChatService` 已按请求挂载受控 callbacks，其余仍待迁移 |
| SSE event 写入与输出限制 | `agent.infrastructure.SseEventWriter` / `ReplyLengthGuard` | 仅规划 |
| 会话记忆与 ownership | `agent.application.SessionContext` + `auth` scope port | 已新增 `AgentRequestScope` 与 ownership verifier，完整 auth 模块迁移待后续 |
| 回复格式、指标一致性和追问守卫 | `agent.ChatReplyGuard` | 已迁移首个低风险切片 |

当前仍保留 `service.ChatService` 作为兼容入口；它通过 `com.brand.agentpoc.agent.ChatReplyGuard` 使用守卫，并为已认证经营分析请求挂载 `agent.infrastructure.ControlledAgentToolCallbacks`，外部 API 和 SSE 协议不变。后续切片应以依赖减少和测试保护为完成条件，而不是为了目录移动而移动。

## 新功能归属规则

* 涉及登录、session 或数据范围：`auth`；涉及组织/经销商范围模型：`organization`。
* 涉及导入、批次、质量：`dataimport`；涉及 KPI 事实和查询：`metrics`。
* 涉及页面汇总：`dashboard`；涉及分析计划、分类、规则事实：`analytics`。
* 涉及对话、模型、工具、会话、SSE：`agent`；涉及模板/导出：`reporting`；涉及非结构化知识检索：`knowledge`。
* 如果一个功能横跨模块，先定义 owning module，再通过 application port 调用其他模块；不要在 Controller 中拼接多个模块的底层数据。

## 迁移与回滚策略

每个切片都应先移动实现、调整 import 和测试，再运行针对性测试、PMD 和全量后端测试。迁移失败时只回滚当前切片，不回滚 P1-1 数据库迁移。完成多个稳定切片后，再评估是否引入 Spring Modulith 做依赖验证；本阶段不增加该运行时依赖。
