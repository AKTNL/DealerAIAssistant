# P2-4C 健康检查、告警与性能运行手册

## 1. 适用范围

本手册定义应用存活、接流量条件、依赖降级、Prometheus 告警、Alertmanager 噪声控制和性能基线。它延续 P2-4A 的安全观测契约：metrics 只使用低基数结果标签，不记录 tenant/user ID、SQL、token、prompt、响应正文或报告内容。

生产仍默认只暴露 `health,info`。抓取 Prometheus 前必须通过内网监听、反向代理鉴权或防火墙保护 `/actuator/**`，再显式设置 `MANAGEMENT_ENDPOINTS_WEB_EXPOSURE_INCLUDE=health,info,prometheus`。

## 2. Probe 契约

| 用途 | 标准端点 | 主端口短路径 | 成员 | 失败动作 |
| --- | --- | --- | --- | --- |
| liveness | `/actuator/health/liveness` | `/livez` | `livenessState` | 进程确实不可恢复时才重启 |
| readiness | `/actuator/health/readiness` | `/readyz` | `readinessState,db,migration,knowledge` | 立即停止新流量，不循环重启 |
| 综合诊断 | `/actuator/health` | 无 | 全部 HealthIndicator | 只用于诊断；`DEGRADED` 映射 HTTP 200 |

推荐编排参数：

```yaml
livenessProbe:
  httpGet: { path: /livez, port: 8081 }
  initialDelaySeconds: 30
  periodSeconds: 10
  failureThreshold: 3
readinessProbe:
  httpGet: { path: /readyz, port: 8081 }
  initialDelaySeconds: 10
  periodSeconds: 5
  failureThreshold: 2
```

模型 provider、数据导入、报告 job 和投递通道都不属于 liveness。模型短暂不可用时继续通过确定性分析提供服务，禁止因 provider 告警重启应用。

## 3. 健康与降级语义

| 依赖 | 信号 | 状态语义 | 是否阻止流量 | 责任边界 |
| --- | --- | --- | ---: | --- |
| PostgreSQL | Actuator `db`、Hikari metrics | 连接失败为 `DOWN` | 是 | DBA/基础设施恢复数据库；应用不自动修复 |
| Flyway | `migration` HealthIndicator | 有 pending migration 为 `OUT_OF_SERVICE`，检查失败为 `DOWN` | 是 | 发布负责人核对版本和迁移日志 |
| PGvector/知识索引 | `knowledge` HealthIndicator | 索引未初始化为 `OUT_OF_SERVICE` | 是 | AI/知识负责人核对扩展、表、embedding 与 catalog |
| 模型 provider | `agentpoc.model.call` error ratio | 失败率升高为降级；规则分析继续可用 | 否 | AI 平台处理 provider、网络、配额；应用保留 fallback |
| 数据导入 | `agentpoc.data.import` outcome | `fallback/error` 表示数据可能模拟、陈旧或不可用 | 否 | 数据运营修复工作簿/字段；生产不允许 fallback |
| 报告 job | backlog/retry/failure gauges | 超阈值时综合健康为 `DEGRADED` | 否 | 报告服务负责人处理订阅、权限、lease 与生成失败 |
| 投递通道 | backlog/retry/failure gauges | permanent/unknown 持续存在为 `DEGRADED` | 否 | 通知负责人核对 SMTP、收件人和 UNKNOWN 回执 |

`operationalQueue` 只加入综合诊断，不加入 readiness。数据库不可用时 readiness 已由 `db` 拒绝流量，队列指标刷新失败不会制造第二个重启信号。

## 4. 指标目录

| 指标 | 含义 |
| --- | --- |
| `http_server_requests_seconds_*` | HTTP/SSE 延迟、吞吐、状态码；已启用直方图 |
| `hikaricp_connections_*` | 连接池 active/max/pending/timeout |
| `agentpoc_database_query_seconds_*` | Spring Data repository 调用时延，不记录方法名或 SQL |
| `agentpoc_database_slow_query_total` | 超过 `APP_OBSERVABILITY_SLOW_QUERY_THRESHOLD` 的调用数，默认 `500ms` |
| `agentpoc_model_call_seconds_*` | provider 同步/流式调用最终时延与 success/error/cancelled |
| `agentpoc_data_import_seconds_*` | 导入耗时与 success/error/fallback/skipped |
| `agentpoc_report_job_backlog` / `retry` / `failure` | READY+RETRY_WAIT、重试等待、永久失败数量 |
| `agentpoc_report_delivery_backlog` / `retry` / `failure` | READY+SENDING+RETRY_WAIT、重试、永久/UNKNOWN 数量 |
| `agentpoc_operational_queue_refresh_available` | 数据库队列快照是否刷新成功 |

队列默认每 30 秒刷新。可用 `APP_OBSERVABILITY_QUEUE_REFRESH_INTERVAL` 调整；不要设置成高频数据库轮询。

## 5. 告警接入与噪声控制

Prometheus 规则位于 `ops/prometheus/agentpoc-alerts.yml`。部署前必须：

1. 用 Blackbox Exporter 探测 `/readyz`，并给目标增加 `job="blackbox",probe="agentpoc-readiness"` 标签。
2. 把 `grafana.example.invalid` 与 `runbooks.example.invalid` 替换为实际只读诊断页和本手册发布地址。
3. 使用 `promtool check rules` 校验，再在测试环境通过受控故障演练验证 firing/resolved。

Alertmanager 模板位于 `ops/alertmanager/alertmanager.example.yml`：

* 同一 `alertname/service/cluster` 先等待 30 秒聚合，5 分钟内合并变化。
* warning 默认 4 小时才重复，critical 为 1 小时；避免重复事件通知风暴。
* 同实例 critical 会抑制 warning，防止数据库故障同时产生大量下游告警。
* webhook 使用 `url_file` 读取 secret，并设置 `send_resolved: true` 发送恢复通知。

模板不是收件人组织承诺。实际 webhook secret、升级路径和 24x7 值班由部署环境负责。

## 6. 告警与处置

| 告警 | 阈值/去抖 | 第一诊断 | Owner |
| --- | --- | --- | --- |
| `AgentPocReadinessFailed` | 连续 2 分钟 | 查 `/readyz`、数据库、Flyway、知识启动日志 | 应用 + DBA/AI 知识 |
| `AgentPocHttpErrorRateHigh` | 10 分钟 5xx > 5%，持续 10 分钟 | 按 route/status 查 HTTP 面板，再用 traceId 定位 | 应用 |
| `AgentPocHttpLatencyHigh` | 非 SSE p95 > 2s，持续 10 分钟 | 对比 repository、Hikari、GC 和最慢 route | 应用 + DBA |
| `AgentPocSseLatencyHigh` | SSE p95 > 30s，持续 15 分钟 | 区分模型、工具、网络断开和未结束流 | 应用 + AI 平台 |
| `AgentPocSlowQueriesDetected` | 10 分钟至少 5 次，持续 5 分钟 | 查同时段 route/trace；在数据库侧执行受控 EXPLAIN | DBA + 应用 |
| `AgentPocModelProviderDegraded` | 10 分钟 error > 20%，持续 10 分钟 | 核对 provider 可达性、配额、模型配置；确认 fallback 成功 | AI 平台 |
| `AgentPocImportFailures` | 30 分钟至少 2 次 fallback/error | 查导入错误码、文件与字段校验；禁止记录业务行 | 数据运营 |
| `AgentPocReportJobBacklog` | backlog >= 50，持续 10 分钟 | 查 runner 是否启用、READY/RETRY_WAIT、lease 与权限 | 报告服务 |
| `AgentPocReportDeliveryFailures` | failure >= 1，持续 10 分钟 | 区分 permanent/UNKNOWN；UNKNOWN 不自动重放 | 通知服务 |
| `AgentPocConnectionPoolSaturated` | active/max > 85% 且 pending > 0，持续 5 分钟 | 查慢查询、事务时长、连接泄漏和数据库容量 | DBA + 应用 |
| `AgentPocJvmHeapPressure` | heap > 90%，持续 10 分钟 | 查 GC、并发 SSE、会话和批量响应；保留 heap 证据策略 | 应用/基础设施 |

慢查询 metric 不包含 SQL。排查人员只能从同时间窗的安全 route/trace 进入数据库侧查询统计；禁止临时把 SQL 参数、请求正文或 tenant/user ID 加成 Prometheus 标签。

## 7. 性能基线

工具：`ops/performance/baseline.mjs`，依赖 Node.js 20+，不增加 npm 依赖。它覆盖 Dashboard、机会明细、Agent 查询和报告生成，仅读取响应以释放连接，不打印或持久化响应正文。报告场景会创建草稿，所以只能在隔离性能环境运行，并要求显式设置 `ALLOW_REPORT_WRITES=true`。

```powershell
$env:BASE_URL = 'https://staging.example.com'
$env:ACCESS_TOKEN = '<short-lived performance user token>'
$env:TENANT_KEY = '<performance tenant key>'
$env:ALLOW_REPORT_WRITES = 'true'
$env:DURATION_SECONDS = '300'
$env:CONCURRENCY = '10'
$env:OUTPUT_PATH = 'artifacts/performance-baseline.json'
node ops/performance/baseline.mjs
```

2026-08-16 本地回归基线使用 Java 21、H2、bundled 非生产测试数据、20 秒和并发 2；warm-up 不计入样本：

| 路径 | 样本 | p50 | p95 | p99 | 错误率 | 门槛 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Dashboard | 47 | 219.578ms | 230.264ms | 249.499ms | 0% | p95 <= 750ms |
| 数据详情 | 48 | 39.312ms | 46.185ms | 63.504ms | 0% | p95 <= 1000ms |
| Agent 查询（确定性 fallback） | 48 | 49.831ms | 54.603ms | 55.667ms | 0% | p95 <= 5000ms |
| 报告生成 | 48 | 504.494ms | 533.076ms | 545.557ms | 0% | p95 <= 1500ms |

最慢路径为报告生成。该结果用于代码回归，不代表生产容量。发布前必须在 PostgreSQL/PGvector 预发环境使用隔离 tenant、真实网络拓扑和预期并发重跑至少 5 分钟，并同时观察 Hikari、repository、heap 与 model provider；不得用本机 H2 结果推导实例数。

## 8. 受控告警演练

所有演练只在隔离测试环境执行，不让健康检查执行修复：

1. 暂停测试数据库网络：`/readyz` 应返回 503，`/livez` 仍保持 200，编排停止流量但不重启。
2. 指向不可达的测试模型 endpoint：业务应走 fallback；模型错误率达到窗口后告警，不影响 readiness。
3. 将测试 job 置于 READY/RETRY_WAIT 或 delivery 置于受控失败状态：对应 gauge 和告警触发，清理/重试后发送 resolved。
4. 临时把测试环境慢查询阈值调为 `1ms`：产生至少 5 个 repository 调用并验证告警；演练后恢复 `500ms`。
5. 连续执行两次缺失测试工作簿导入：local 可验证 fallback 告警；prod 必须失败且不得生成模拟数据。

每次演练保留时间窗、alert firing/resolved 截图、trace/request ID 和修复动作，不保留 token、prompt、SQL 参数或业务响应。

## 9. 回滚

1. 告警噪声异常时先禁用对应 Prometheus rule group，不修改应用业务数据。
2. 队列刷新压力过大时提高 `APP_OBSERVABILITY_QUEUE_REFRESH_INTERVAL`；不要关闭 readiness 的 `db/migration/knowledge`。
3. Repository metric 开销异常时提高 `APP_OBSERVABILITY_SLOW_QUERY_THRESHOLD`，保留基础 query timer 以便对比。
4. 永远不要把模型 provider 加入 readiness/liveness。回滚模型观测时仍保留确定性 fallback。
5. 恢复后重新加载规则，确认 Alertmanager 发出 resolved 且没有重复通知风暴。
