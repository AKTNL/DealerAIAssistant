# 经销商 AI 分析助手重构文档

本目录用于承接项目从 POC 到更贴近真实项目的重构工作。旧的 POC 设计和实施计划已经清理，当前保留的原始基线是 `Agent-POC-需求文档.docx`。后续新增文档应围绕真实开发协作、拆任务和验收，而不是复述 POC 演示说明。

## 阅读顺序

| 顺序 | 文档 | 用途 |
| --- | --- | --- |
| 1 | `00-重构总览.md` | 理解重构目标、边界、阶段和优先级 |
| 2 | `03-数据重构需求.md` | 明确数据源、实体、缺失值和真实数据迁移方向 |
| 3 | `02-后端重构需求.md` | 明确 API、服务边界、AI/规则链路和安全配置 |
| 4 | `01-前端重构需求.md` | 明确页面体验、状态管理、SSE 消费和 UI 验收 |
| 5 | `04-联调方案.md` | 明确本地、接口、SSE、模型服务和数据联调流程 |
| 6 | `05-测试验收方案.md` | 明确自动化、准确率题库和人工验收门槛 |

## 当前可信来源

| 来源 | 状态 | 使用方式 |
| --- | --- | --- |
| `Agent-POC-需求文档.docx` | 保留 | 作为 POC 需求基线，不直接等同于生产目标 |
| `README.md` | 保留但仍是 POC 视角 | 作为当前实现事实来源，后续需要更新定位 |
| 当前前后端代码 | 保留 | 作为真实现状来源，优先级高于旧设计想法 |
| `.trellis/spec/` | 保留 | 作为实现规范来源，真正改代码前必须读取 |

## 文档编写原则

1. 区分 `当前 POC 已有`、`真实项目目标`、`暂不做`。
2. 优先写可拆任务的内容：边界、输入输出、验收、风险。
3. 不把 POC 里的演示做法包装成生产方案。
4. 数据口径优先于页面表现，避免漂亮但不可解释的分析结果。
5. 每次实际重构前，回到对应文档确认范围，再进入代码修改。

## 第一阶段文档目标

本批文档不是最终投产方案，而是重构前的工作地图。它应该回答：

* 我们现在有什么？
* 哪些只是 POC 便利做法？
* 真实项目要补什么？
* 哪些任务应该先拆？
* 怎么验证改造没有破坏现有可演示能力？

## 后续维护方式

* 新需求先进入对应主题文档的 `待拆任务` 或 `开放问题`。
* 已确认的架构或口径决策写入对应文档的 `目标状态` 或 `决策记录`。
* 实现过程中发现新的代码约定，写入 `.trellis/spec/`，不要只写在 `docs/`。
* README 等项目入口文档应在核心方向稳定后统一更新。
