# MVP 试点验收脚本

本文用于把 P0 Dashboard MVP 从“功能已完成”推进到“可以重复演示、可以记录反馈、可以决定 P1 优先级”的试点验收闭环。

## 使用场景

本脚本优先服务内部演示验收，同时保留真实业务用户反馈字段。一次验收应该回答：

* 业务用户是否能在 30 秒内从 Dashboard 发现一个经营问题？
* Dashboard 指标和 AI/规则分析解释是否一致？
* 分析回答是否明确数据来源、口径、限制和置信度？
* 哪些反馈应该进入 P1：筛选、趋势、下钻、报告草稿、真实数据接入或工程化底座？

## 验收范围

包含：

* 登录和 Dashboard 默认首屏。
* 数据状态、active batch、模拟数据和质量问题提示。
* 目标达成、商机漏斗、线索来源、跟进任务、活动效果等核心模块。
* Dashboard 到 AI 分析的入口。
* 反馈记录和 P1 候选任务排序。

不包含：

* 持久化数据库、迁移工具或真实数据接入。
* 完整账号、权限、组织树、审计、多租户。
* 受控 Agent、RAG 知识库、自动报告导出。
* 用人工验收替代已有自动化回归。

## 环境准备

### 后端

在 PowerShell 中：

```powershell
cd backend
$env:APP_AUTH_BOOTSTRAP_USERNAME="admin"
$env:APP_AUTH_BOOTSTRAP_PASSWORD="temporary-password"
$env:APP_AUTH_BOOTSTRAP_DISPLAY_NAME="Local Administrator"
mvn "-Dfrontend.skip=true" spring-boot:run
```

预期：

* 后端监听 `http://localhost:8081`。
* 启动时导入 `classpath:Sample Data.xlsx`，或在 demo 模式回退到内置样例数据。
* 登录后 `GET /api/data-status` 可以查看数据来源、导入批次和质量问题。

### 前端

在另一个终端中：

```powershell
cd frontend
npm ci
npm run dev
```

预期：

* 前端监听 `http://localhost:5173`。
* Vite 将 `/api` 代理到 `http://127.0.0.1:8081`。

### 登录

打开 `http://localhost:5173`，输入初始化用户名和临时密码：

```text
admin / temporary-password
```

预期：首次登录进入强制改密视图；改密后使用新密码重新登录，默认进入 Dashboard。

## 端到端验收步骤

| 步骤 | 操作 | 预期 | 记录 |
| --- | --- | --- | --- |
| 1 | 启动后端 | 无启动失败；导入数据或明确 fallback | 记录命令和数据来源 |
| 2 | 启动前端 | 首页可访问，无 Vite 代理错误 | 记录访问地址 |
| 3 | 登录与首次改密 | 正确用户凭据进入强制改密；改密重登后进入工作台；错误凭据不进入 | 记录登录结果 |
| 4 | 查看数据状态 | 能看到 active batch、模拟数据、质量问题或 fallback 警告 | 记录是否影响可信度 |
| 5 | 查看 Dashboard | 核心 KPI、排名、漏斗、来源、任务、活动模块可见 | 记录 30 秒内发现的问题 |
| 6 | 触发分析入口 | 从 Dashboard 发起至少 1 个预置分析问题 | 记录问题文本和入口模块 |
| 7 | 查看分析回答 | 回答包含结论、数据支撑、限制、置信度和追问 | 记录是否可信 |
| 8 | 填写反馈 | 记录有用洞察、不清晰口径、不可信建议和 P1 需求 | 汇总到反馈表 |

## P1 候选排序规则

试点后按以下维度给每个 P1 候选项打分，优先处理总分高且依赖少的任务：

| 维度 | 说明 | 分值 |
| --- | --- | ---: |
| 用户价值 | 是否直接解决验收中的高频痛点 | 1-5 |
| 可信度提升 | 是否提升指标口径、数据来源或限制说明可信度 | 1-5 |
| 试点阻塞程度 | 不做是否会阻塞真实/脱敏数据试点 | 1-5 |
| 工程依赖 | 是否依赖数据库、权限、真实数据或架构重构 | 1-5，分高表示依赖更重 |
| 实施复杂度 | 预估工程量和回归风险 | 1-5，分高表示更复杂 |

建议排序公式：

```text
优先级分 = 用户价值 + 可信度提升 + 试点阻塞程度 - 工程依赖 - 实施复杂度
```

初始候选项：

| P1 候选 | 触发信号 | 备注 |
| --- | --- | --- |
| 筛选和范围控制 | 用户无法只看区域/门店/时间段 | 可能先做轻量前端筛选，再接后端查询条件 |
| 趋势分析 | 用户想知道问题是单点还是持续恶化 | 依赖时间序列口径和图表 |
| 明细下钻 | 用户不信聚合结论，想看支撑行 | 依赖分页 API 和权限边界 |
| 报告草稿 | 用户希望把洞察带走或汇报 | 可先 Markdown，后续再 PDF/Word |
| 真实/脱敏数据接入 | 用户愿意继续试点 | 依赖字段映射、质量报告和持久化方案 |
| 持久化数据库和迁移 | 多批数据、真实试点和历史对比需要 | 是工程底座，适合在试点反馈明确后推进 |
